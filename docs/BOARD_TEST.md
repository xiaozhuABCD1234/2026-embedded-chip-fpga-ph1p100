# 板测数据汇总

所有数字都来自 Orange Pi 5 Max（RK3588）实板。**除特别标注外，实测口径是 1080p ROI 双路**；
4K 全帧通路已在 RTL 里改好但**没有任何板测数字**，本文件不写 4K 实测值。

## 2. MCLK 扫频（选定 27 MHz / 891 Mbps）

| MCLK | 寄存器表 | 链路 | sensor VSYNC | writer | 结论 |

## 3. 双路 30 fps 采集（sensor → DDR3）

| 项 | A | B |
|---|---:|---:|
| 60.639 s 帧数 | 1819 | 1819 |
| 帧率 | **29.997 fps** | **29.997 fps** |
| 每 10 s 增量 | 303~304 | 303~304 |
| verdict `0xF4`/`0x184` | 0x20 | 0x20 |
| 丢组 `0x1A4`/`0x1C4` | 0 | 0 |

带宽 $2 \times 29.997 \times 2{,}592{,}768 \approx 155.6\ \mathrm{MB/s}$，占 Gen2 ×2 可用带宽约 15.6%。

两路帧逐字节比较 2,290,823 / 2,592,768 字节不同（88.4%），是两条独立通路，不是同一缓冲的重复抓取。

### 打包吞吐瓶颈（已修）

旧打包器 `pay_room=(bcnt<=3)` 与 `word_take=(bcnt>=4)` 天然互斥，每帧事件数 = 518,400 次 pop + 648,192 次取字 = **1,166,592 拍/路/帧**；
一帧 33.2 ms × 100 MHz = 3,320,000 拍，两路合计 70% 占用 → 两路相位一撞就 FIFO 溢出丢组。
改成 128 bit 字节缓冲、允许同拍 pop + 取字后，每帧降到 **648,192 拍**，两路合计 39%，余量 61%。

决定性对照（同一套寄存器/流程，只换打包节拍）：

| | 旧节拍 | 新节拍 |
|---|---|---|
| A `0xA0` 发布序号 | 恒 0（40 s 不涨） | 30.1 fps |
| 每帧 push / drop | 359,227 / 159,173 | 518,400 / 0 |
| 打包占用 `0x1B4` | 4,208,399 拍（> 1 帧周期） | ≈3,335,3xx（≈1 帧周期） |

`push + drop = 518,400` 严格成立，说明丢在 FIFO 满，不在相机侧。

`BURST_GROUPS` 从 410 提到 820 会打坏单路（帧尾凑不够门槛 → 写者停发 → 相机写满 FIFO 丢 EOF → 超时补零）；
可行区间是 [≈410, ≈512]，不能靠加大门槛解决吞吐。

## 4. 主机取流

| 口径 | 结果 |
|---|---|
| 纯取帧（`--scale 8`） | **30.4 pair/s**，已到源端上限 |
| 连续 600 次双路取帧 | 600 成功 / 0 失败，180 s（≈3.3 pair/s，含进程启动与两帧 PGM 写盘） |
| 逐帧核对 | 20 次 A/B `capture_seq` 全相同，门铃同步 +1 |
| 单次进程墙钟 | 0.08~0.12 s |

30 对交替 one-shot（单槽时代）的耗时分解：一对 A+B 224.95 ms（p95 257 ms），其中 A 等新帧 34.69 ms、
B 等新帧 22.19 ms、每帧取帧+校验+写 PGM 约 46 ms。

## 5. display 推流（1080p 双路）

| 输出 | 每对耗时 | 帧率 |
|---|---:|---:|
| 1920×1080 彩色 | ~90 ms | **11 pair/s** |
| 960×540 彩色（`--scale 2`） | ~43 ms | **23 pair/s** |
| 1920×1080 灰度（`--bayer gray`） | ~58 ms | ~17 pair/s |

1080p 分段耗时（`DISPLAY_DEBUG_TIMING=1`）：去马赛克 26 ms、后处理 21 ms、RGB→NV12 13 ms、硬件 JPEG 21 ms。

优化过程（同一硬件逐项量出来）：200 ms（串行编码 + 每对固定 20 ms 释放等待）→ 185 ms（流水线 + A/B 两核并行）
→ 121 ms（释放等待 20→5 ms）→ 95 ms（去马赛克改算术实现）→ 90 ms（高光去饱和并入查表循环）。
瓶颈已经从 JPEG 变成 CPU 像素处理；PCIe 和相机都不是限制。

- 长跑：2 分 25 秒推 616 对，`/stats` 的 `a_seq` 与 `b_seq` 始终相同。
- 驱动把 1080 对齐到 1088，上报的是真实尺寸 1920×1088。
- 两个 `/dev/video4` 实例并行编码实测 37 ms/对，比单实例串行 29 ms/对更慢，所以保持共用实例 + Mutex。

## 8. 硬件同步

`0x1E4=0x8000D`、`0x1E8` 稳定 2~3 tick（62.5 MHz，约 32~48 ns）、miss/overrun=0、abort/restart 通过。
详见 [HARDWARE_SYNC](HARDWARE_SYNC.md) 与 `log/sync/RESULTS.md`。

## 9. 未验证

- **4K 全帧**：无任何板测数字（帧率、CRC、带宽、DDR 占用都没测）。
- 4K + 硬件同步组合；`SKIP_ROWS=37` 在 4K 下未复测。
- MSI 中断路径（当前 `use_irq=0`，走 mailbox 轮询）。
- 故意丢帧 / 断链故障注入；60 s 以上长稳。
- 单路 B 的完整回归（RKA1 状态回读仍指向 A 片）。
- CCM / 镜头校正 / 24 色卡标定；10bit 通路。
