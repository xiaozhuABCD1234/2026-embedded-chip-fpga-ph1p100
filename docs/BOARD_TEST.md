### 打包吞吐瓶颈（已修）

旧打包器 `pay_room=(bcnt<=3)` 与 `word_take=(bcnt>=4)` 天然互斥，每帧事件数 = 518,400 次 pop + 648,192 次取字 = **1,166,592 拍/路/帧**；
一帧 33.2 ms × 100 MHz = 3,320,000 拍，两路合计 70% 占用 → 两路相位一撞就 FIFO 溢出丢组。
改成 128 bit 字节缓冲、允许同拍 pop + 取字后，每帧降到 **648,192 拍**，两路合计 39%，余量 61%。

决定性对照（同一套寄存器/流程，只换打包节拍）：

| | 旧节拍 | 新节拍 |
|---|---|---|
| A `0xA0` 发布序号 | 恒 0（40 s 不涨） | 30.1 fps |
| 每帧 push / drop | 359,227 / 159,173 | 518,400 / 0 |
| 打包占用 `0x1B4` | 4,208,399 拍（> 1 帧周期） | ≈3,335,3xx（≈1 帧周期） |

`push + drop = 518,400` 严格成立，说明丢在 FIFO 满，不在相机侧。

`BURST_GROUPS` 从 410 提到 820 会打坏单路（帧尾凑不够门槛 → 写者停发 → 相机写满 FIFO 丢 EOF → 超时补零）；
可行区间是 [≈410, ≈512]，不能靠加大门槛解决吞吐。

| 输出 | 每对耗时 | 帧率 |
|---|---:|---:|

## 8. 4K30 全帧（单路，已通）

传感器固定 4K30 全阵列输出，每行 CSI-2 长包 WC=4830 字节 = **3864 像素**
（3840 有效 + 左右各 12 列 OB），每帧 **2192 行**（2160 有效 + 上下各 16 行 OB）。

| 项 | 值 |
|---|---|
| 窗口 | `X0=0, X_OFF=12, Y0=0, SKIP_ROWS=16` → 2160×960 组，无行/列错位 |
| 每帧组数 `0x1A0` | **2,073,600** = 2160×960，正好等于 `GROUP_TOTAL` |
| 丢组 `0x1A4` | **0** |
| AXI 拍数 `0xF0` | 324,096 = 10,371,072 B / 32 B |
| 帧率 | 29.9 fps（`0xA0` 690 s 内涨 ~20.6k） |
| R10F CRC | payload/header 双层逐字节复算通过 |
| 主机取帧 | `frame_grab -t 5000` 一次性成功，一致性检查 OK |
| 端到端延迟 | **52.6 ~ 55.2 ms**（SOF→主机拿到帧，3 次取帧） |
| 计数器频率 | 实测 99.92 MHz（标称 100 MHz） |

帧合同：3840×2160 packed RAW10，stride 4800 B，payload 10,368,000 B，128 B 头 +
4 KiB 对齐 ⇒ 10,371,072 B/帧，81,024 笔 128 B MWr。

延迟拆解（$T_{\text{E2E}} = 52.6\text{–}55.2\ \mathrm{ms}$）：

- 传感器整帧读出 2192 行 × 14.8 µs ≈ **32.4 ms** —— 这段时间里 FPGA 才开始收尾；
- 其余 **≈20 ms** 是打包 + DDR3 写 + 推帧（10.37 MB / 20 ms ≈ 519 MB/s，已接近 Gen2×2 可用带宽）。

所以「传输段」本身约 20 ms，满足 ≤50 ms；但从 SOF 计时就超过 50 ms，因为 4K 一帧
本身就要读 32 ms。要压到 50 ms 以内只有两条路：流式推帧（不等 EOF 就开始发），或者
降到 1080p（读出 16.7 ms + 传输 5 ms ≈ 22 ms）。后续会给 writer 补 EOF 时间戳，
把「传输段」直接测出来，不再靠减法。

**几何修正（本次板测纠正）**：旧参数 `SKIP_ROWS=37` 来自 1080p ROI 时代，
2192−37 只有 2155 行，每帧短 5 行；`X0=0` 则吃掉左 12 列 OB、丢掉右 12 列有效像素。
正确值是物理原点 (12,16)。为避免 R10F 头里的 `roi_x` 被写成 12，writer 新增
`X_OFF` 参数：它只平移取数窗口，`roi_x` 仍写 0。

### 判定字的假报警（已修）

4K 下每帧 `0xF4` 都读 0x01（`p_bad`），但 `gcnt`、`beats`、`eof` 全部正确、
payload 恰好 10,368,000 B。根因：`pay_ok` 在载荷用满后为假，帧尾仍会到达的组
走"超预算 → 丢弃 + 置 p_bad"分支；而判据把这个事件当整帧作废，于是 0 帧发布。
现在作废判据只看计数（组数 / AXI 拍数 / EOF / AXI 错），`p_bad` 与它的来源位
（`pbad_rsn`，出在 `0x1BC[9:5]`：bit0 blk_locked、bit1 超预算、bit2 eof_bad、
bit3 帧内 SOF、bit4 标记超时）只做诊断。

### 双路 4K 还不成立

两片 writer 同时 4K30 时 A 路每帧 `push=1,583,646 / drop=485,410`（23% 丢组），
出图是横条纹。瓶颈是**打包节拍**不是 DDR：1080p 时每帧 648,192 拍（两路占 39%），
4K 组数是 4 倍 ⇒ 单路 ≈2.59M 拍/帧 = 78% 占用，两路 156% —— 必然溢出。
单路因此是完好的（78% < 100%）。要双路 4K，先把打包器做到每拍多组
（或把打包时钟提到 200 MHz），并把 FIFO 从 1 行（1024 组）加深。

当前默认 arm 掩码改成只开 A（`CAM_ARM_DEFAULT=2'b01`）。运行时写 `0x6C` 会在
帧中途摘掉一路的 arm，实测会让两路都停发（仲裁/发布挂住），要换路请用复位，
不要热改 `0x6C`。

## 9. 硬件同步（未闭合）

1080p 时代曾锁上（`0x1E4=0x8000D`、skew 2~3 tick）。4K 下 `sync start` 走到
WARM 就报 `error_code=5`（等 pair 超时）：`miss_a=0`、`miss_b` 每个 A 帧 +1，
即 **A 出帧、B 一帧不出**。

已排除：B 的 I2C（14 笔角色写全 ACK、`cfg_done=1`、error 不是 2/3）、B 的 PHY
（`SYNC_ENABLE=0` 时 B 自由跑完全正常：`0x84=0xcfee15bf` lane=0xF/in_frame=1，
`0x128` good 包持续增长，`0x12C` 同样 2192 行 × 4830 B）、FPGA 侧的配对/门控逻辑
（iverilog 跑 `tb_sync_offline` 在"B 有 SOF"前提下能锁）。

也就是说：B 切成 slave（`0x3003=1`）后拿不到可用的 A XVS/XHS。FPGA 没有
XVS/XHS 引脚，SOF 只来自 CSI 的 FS 包 —— 所以这条同步是**板级飞线**的事，
要用示波器确认 A 的 XVS 是否真的到了 B 的 XHS/XVS、电平与极性是否匹配。

## 12. LZ77 硬件压缩（通路接好，尚未出流）

已接入：

~~~text
A 路组流 → codec_roi_crop(1920×544，中心) → a1_frame_top(a1_deflate_core)
         → codec_pack(拼成 1920×1088 定长帧) → algo_y8_to_legacy → A 路 writer → 主机
~~~

压缩字节直接放进 8bit 采样位，主机按 `0x250`（压缩字节数）截前 N 字节后 zlib 解压，
再用 `0x254`（原始长度）与 `0x258`（原始 CRC32）核对。

| 寄存器 | 含义 |
|---|---|
| `0x240[0]` | 0 = 预处理帧，1 = LZ77 压缩流 |
| `0x240[3]` | keep_div：0 = 每帧压，1 = 隔帧压 |
| `0x250` | CODEC_STREAM_LEN（压缩后字节数，0 = 本帧没压出来） |
| `0x254/0x258` | CODEC_RAW_LEN / CODEC_RAW_CRC |
| `0x25C` | {fed[15:0], aborts[15:0]} |

**当前状态：能出流，但打包与压缩率都不对。**

已修复的根因：`codec_roi_crop` 的 FIFO 元素是 43 位，写入的 `{pending_sof, cam_pix}`
只有 41 位（落到 [40:0]），读出却取 `[42]` —— 永远读到 0。`a1_frame_top` 靠 `in_sof`
启动一帧，于是它从没开始过。改成 `{2'b00, pending_sof, cam_pix}` + 读 `[40]` 后，
板测立刻出流：`st_stream_len=326,742`、`st_raw_len=329,120`。

还没解决的（按优先级）：

1. **打包器没处理 abort**：编码器 abort 一帧后不会给 `c_last`，codec_pack 永远等不到，
   writer 就停在半帧、不再发布（板测 `0xA0` 停在 389 后不动）。要接 `frame_abort` 并丢弃半帧。
2. **压缩率只有 0.7%**（326,742 / 329,120），说明 deflate 走了 stored 分支；而且 raw_len
   只有预期的 1/4（1,305,600），帧本身也不完整。
3. 吞吐：1920×544@30 = 78.4 MB/s 对编码器 78.5 MB/s 余量太小，`proto_abort` 频繁，
   现在只能靠 `0x240[3]=1` 隔帧压（15 fps）。

历史上排查过的（都已修）：SOF 与首组同拍、补零阶段死锁、`widx%GPQ` 除法器导致
SWNS −0.149 ns。

**历史状态（修复前）：未出流。** 板测：裁剪器按 30 fps 送帧（`fed` 每秒 +30），
`aborts=0`，但 `stream_len/raw_len` 恒 0 —— 编码器收下数据却从不结束一帧。
已排除的：裁剪组的组数（261,120 = 1920×544/4）、SOF 与首组同拍（a1_frame_top 把
SOF 那拍当第一个采样，原来多送了一个空 SOF 组，已修）、补零阶段的死锁（已修）、
吞吐（544 行只要 39 MB/s，编码器 78 MB/s）。

下一步要在 iverilog 里把 crop + a1_frame_top + pack 串起来跑合成相机流，
定位是编码器内部状态机卡住还是输入握手丢拍——上板盲试已经花了 7 个位流。

**时序**：这一版 `SWNS = -0.149 ns`（不收敛），原因是 codec_pack 里的
`widx % GPQ` 综合出了除法器。应改成列计数器（到 GPQ-1 归零），下一版修正。

**吞吐账**（为什么 ROI 只有 544 行）：`a1_deflate_core` 实测 2.39 cycle/byte，
187.5 MHz 下 78.5 MB/s；1920×1088@30 要 78.3 MB/s（余量 0.3%），1920×544@30 只要 39.2 MB/s。
4K 整帧（311 MB/s）需 744 MHz，不可能。
