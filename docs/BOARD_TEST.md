## 3. 双路 30 fps 采集（sensor → DDR3）

| 项 | A | B |
|---|---:|---:|
| 60.639 s 帧数 | 1819 | 1819 |
| 帧率 | **29.997 fps** | **29.997 fps** |
| 每 10 s 增量 | 303~304 | 303~304 |
| verdict `0xF4`/`0x184` | 0x20 | 0x20 |
| 丢组 `0x1A4`/`0x1C4` | 0 | 0 |

带宽 $2 \times 29.997 \times 2{,}592{,}768 \approx 155.6\ \mathrm{MB/s}$，占 Gen2 ×2 可用带宽约 15.6%。
两路帧逐字节比较 2,290,823 / 2,592,768 字节不同（88.4%），是两条独立通路，不是同一缓冲的重复抓取。

### 打包吞吐瓶颈（已修）

旧打包器 `pay_room=(bcnt<=3)` 与 `word_take=(bcnt>=4)` 互斥，每帧 518,400 次 pop + 648,192 次取字 =
**1,166,592 拍/路/帧**；一帧 3,320,000 拍，两路占 70%，相位一撞就 FIFO 溢出丢组。
改成 128 bit 字节缓冲、允许同拍 pop + 取字后，每帧降到 **648,192 拍**，两路占 39%，余量 61%。

决定性对照（同寄存器/流程，只换节拍）：A `0xA0` 从恒 0（40 s 不涨）变为 30.1 fps；每帧 push/drop 从 359,227/159,173 变为 518,400/0；打包占用 `0x1B4` 从 4,208,399 拍（>1 帧周期）降到 ≈3,335,3xx 拍。`push + drop = 518,400` 严格成立，说明丢在 FIFO 满，不在相机侧。

`BURST_GROUPS` 从 410 提到 820 会打坏单路（帧尾凑不够门槛 → 写者停发 → 相机写满 FIFO 丢 EOF → 超时补零）；可行区间是 [≈410, ≈512]，不能靠加大门槛解决吞吐。

## 5. display 推流（1080p 双路）

| 输出 | 每对耗时 | 帧率 |
|---|---:|---:|
| 1920×1080 彩色 | ~90 ms | **11 pair/s** |
| 960×540 彩色（`--scale 2`） | ~43 ms | **23 pair/s** |
| 1920×1080 灰度（`--bayer gray`） | ~58 ms | ~17 pair/s |

1080p 分段（`DISPLAY_DEBUG_TIMING=1`）：去马赛克 26 ms、后处理 21 ms、RGB→NV12 13 ms、硬件 JPEG 21 ms。优化链：200 ms（串行编码 + 每对固定 20 ms 释放等待）→ 185 ms（流水线 + A/B 两核并行）→ 121 ms（释放等待 20→5 ms）→ 95 ms（去马赛克改算术实现）→ 90 ms（高光去饱和并入查表循环）。瓶颈已从 JPEG 变成 CPU 像素处理；PCIe 和相机都不是限制。

- 长跑 2 分 25 秒推 616 对，`/stats` 的 `a_seq` 与 `b_seq` 始终相同；驱动把 1080 对齐到 1088 后上报 1920×1088。
- 两个 `/dev/video4` 实例并行编码 37 ms/对，比单实例串行 29 ms/对更慢，所以保持共用实例 + Mutex。

## 8. 4K30 全帧（单路，已通）

传感器固定 4K30 全阵列：每行 CSI-2 长包 WC=4830 字节 = **3864 像素**（3840 有效 + 左右各 12 列 OB），每帧 **2192 行**（2160 有效 + 上下各 16 行 OB）。

| 项 | 值 |
|---|---|
| 窗口 / 组数 | `X0=0, X_OFF=12, Y0=0, SKIP_ROWS=16`；2,073,600 组 = 2160×960，无行/列错位 |
| 丢组 / AXI 拍数 | **0**；324,096 = 10,371,072 B / 32 B |
| 帧率 / 计数器 | 29.9 fps（`0xA0` 690 s 内涨 ~20.6k）；实测 99.92 MHz（标称 100 MHz） |
| CRC / 主机取帧 | payload/header 双层逐字节复算通过；`frame_grab -t 5000` 一次性成功 |
| 端到端延迟 | **52.6 ~ 55.2 ms**（SOF→主机拿到帧，3 次取帧） |

帧合同：3840×2160 packed RAW10，stride 4800 B，payload 10,368,000 B，128 B 头 + 4 KiB 对齐
⇒ 10,371,072 B/帧，81,024 笔 128 B MWr。延迟拆解 $T_{\text{E2E}} = 52.6\text{–}55.2\ \mathrm{ms}$：
传感器整帧读出 2192 行 × 14.8 µs ≈ **32.4 ms**，其余 **≈20 ms** 是打包 + DDR3 写 + 推帧
（10.37 MB / 20 ms ≈ 519 MB/s，已接近 Gen2×2 可用带宽）。所以传输段约 20 ms，满足 ≤50 ms；
从 SOF 计时必然超过 50 ms。要压到 50 ms 以内只有流式推帧或降到 1080p（读出 16.7 ms + 传输 5 ms ≈ 22 ms）。

**几何修正**：旧 `SKIP_ROWS=37` 来自 1080p ROI 时代，2192−37 只有 2155 行；`X0=0` 吃掉左 12 列 OB、丢右 12 列有效像素。正确物理原点是 (12,16)；writer 新增 `X_OFF` 只平移取数窗口，R10F 头 `roi_x` 仍写 0。

### 判定字的假报警（已修）

4K 下每帧 `0xF4` 读 0x01（`p_bad`），但 `gcnt`/`beats`/`eof` 全对、payload 恰好 10,368,000 B。根因是 `pay_ok` 在载荷用满后为假，帧尾组走「超预算」分支被当整帧作废；现作废判据只看计数，`p_bad`/`pbad_rsn`（`0x1BC[9:5]`：bit0 blk_locked、bit1 超预算、bit2 eof_bad、bit3 帧内 SOF、bit4 标记超时）只做诊断。

### 双路 4K 还不成立

两片 writer 同时 4K30 时 A 路每帧 `push=1,583,646 / drop=485,410`（23% 丢组），出图是横条纹。瓶颈是**打包节拍**不是 DDR：4K 组数是 1080p 的 4 倍 ⇒ 单路 ≈2.59M 拍/帧 = 78% 占用，两路 156% 必然溢出（单路 78% < 100%，所以完好）。要双路 4K，需每拍多组（或打包时钟 200 MHz）并加深 FIFO。

当前默认 arm 掩码只开 A（`CAM_ARM_DEFAULT=2'b01`）。运行时写 `0x6C` 会在帧中途摘掉一路的 arm，实测两路都停发；要换路请用复位。

## 9. 硬件同步（未闭合）

1080p 时代曾锁上（`0x1E4=0x8000D`、skew 2~3 tick）。4K 下 `sync start` 走到 WARM 就报
`error_code=5`（等 pair 超时）：`miss_a=0`、`miss_b` 每个 A 帧 +1，即 **A 出帧、B 一帧不出**。

已排除：B 的 I2C（14 笔角色写全 ACK、`cfg_done=1`、error 不是 2/3）；B 的 PHY（`SYNC_ENABLE=0` 时
B 自由跑完全正常：`0x84=0xcfee15bf` lane=0xF/in_frame=1，`0x128` good 包持续增长，`0x12C` 同样
2192 行 × 4830 B）；FPGA 配对/门控（`tb_sync_offline` 在「B 有 SOF」前提下能锁）。

也就是说 B 切成 slave（`0x3003=1`）后拿不到可用的 A XVS/XHS。FPGA 没有 XVS/XHS 引脚，SOF 只来自 CSI 的 FS 包，所以这条同步是**板级飞线**的事，要用示波器确认 A 的 XVS 是否到了 B 的 XHS/XVS、电平与极性是否匹配。

## 10. 未验证

- 双路 4K（打包节拍不够，见 §8）；4K + 硬件同步组合。
- 4K 长稳（>60 s）与 4K 的温度/功耗；MSI 中断路径（当前 `use_irq=0`，走 mailbox 轮询）。
- 故意丢帧 / 断链故障注入；单路 B 的完整回归（RKA1 状态回读仍指向 A 片）。
- 彩色白平衡：夜间暗场下 `--auto` 偏品红，AWB 参考点不足；正解是 AEC/AGC + 灰世界。CCM / 镜头校正 / 24 色卡标定、10bit 通路也未做。
